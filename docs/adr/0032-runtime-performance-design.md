# 插件与共享运行时的性能设计原则

**状态**　已采纳。适用于 Pi 插件、共享服务以及它们启动的 worker 和子进程。

## 为什么需要这项决策

Navigator 曾为每一行重新查找任务的归属关系。Goal 曾为同时到达的候选操作各启动一个调度器。Background 曾在每个订阅回调里重读同一个收件队列。三处实现都把共享工作放进了会重复调用的函数里。读一次数据库或启动一次进程看起来合理，调用次数却分别取决于列表行数、候选数和打开的会话数。

**一次源状态变化，由拥有该数据的组件核对一次。读取和计算的成本应主要取决于变化的数据量，投递的成本应取决于确实需要更新的接收方。** 对需要现查的数据，先确定谁要求多新的结果，再决定在哪里读、何时失效。

## 实现原则

1. **让界面消费结果，由数据源负责刷新。** 列表、状态栏和订阅回调读取已经准备好的视图。构建列表时，先按作用域一次取得各行共用的数据，再映射到行。按键、主题变化或重复绘制可以重新排版。只有相关源版本变化或调用方显式要求刷新，才重新取数。Navigator 的回归用例连续绘制同一视图 60 次，预期新增的 provider 调用、元数据读取和 SQLite 连接均为 0。[Navigator 与 Goal 的投影预算](../../scripts/performance/README.md)

2. **在分发前共享读取，同时保留会话边界。** 共享服务先处理一批已提交的变更，再把结果投递给可见内容变化的订阅者。并发请求只有在数据源、作用域、版本和新鲜度要求相同时才合并。缓存键应包含影响结果的工作区、所有者或会话身份。Goal 的 16 个等价并发请求只启动一个调度器。这次检查结束后，下一次准入重新核验。Background 的 16 个不同会话则共享一次队列核对，只有任务所属会话收到更新。[Goal 调度器](../../packages/pi-better-goal/test/admission-scheduler.test.ts) · [Background 订阅](../../packages/pi-better-server/test/background-notification-reads.test.ts)

3. **从变化的对象开始更新。** 传递任务 ID、源版本或日志偏移，让读取方能定位发生变化的部分。正常更新只处理增量。首次建立索引、源被替换或确实漏掉事件时，才启动限定范围的重建。重建按批保存进度，期间到达的新提示合并到待处理集合。比如，96 个同级任务中有一个追加日志，只需读取该日志的新增内容，并更新受影响的视图。[增量日志读取](../../packages/pi-better-server/test/runtime-incremental-log.test.ts) · [丢失通知后的修复](../../packages/pi-better-server/test/runtime-file-repair.test.ts)

4. **只为可推进的工作唤醒进程。** 把调度放在掌握任务状态和截止时间的所有者处。优先由变更通知或最近的有效截止时间唤醒它。必须轮询时，先用索引判断有无合格对象，再做核验、领取或写入，并规定每轮上限和停止条件。待投递队列曾因历史事件仍处于 pending 而反复尝试领取。现在只选择当下能接收事件的对象。会话关闭时撤销其监听和定时器，仍在运行的后台任务由监督者继续负责。[待投递事件筛选](../../packages/operation-coordinator/tests/outbox-poll.test.ts) · [运行时与通知](0029-notification-delivery.md)

5. **按用途决定读取成本和新鲜度。** 普通回复和广播可以携带内存计数。详细队列统计由显式诊断请求采集，并发请求共用样本。读取受阻时，返回标明采集时间的旧值或「未知」。停机、恢复执行等决策须按各自约定取得新鲜证据。这次把队列诊断移出广播和普通回复后，同样的 48 次状态变化使 SQLite 日志辅助文件检查从 1,248 次降到 480 次，目标会话仍收到 48 次更新。[读取线程执行策略](../plans/read-model-execution-policy.md) · [诊断回归测试](../../packages/pi-better-server/test/query-executor.test.ts)

6. **限制积压，并为关键操作保留执行机会。** 队列、缓存、重试和单批处理量都应有上限。慢消费者可以合并中间快照，并按版本重新同步。需要持久投递的完成事件按回执恢复。耗时计算移入 worker 后仍须限制并发，让状态查询、取消和到期任务能继续处理。评估成本时，把前台、服务和工作进程的消耗合计在内。[共享工作预算](../../packages/pi-better-server/test/work-budget.test.ts) · [通知投递约定](0029-notification-delivery.md)

## 在功能设计和评审中使用

以新增「当前会话待处理任务数」为例。先确定由掌握队列变更的组件按会话维护计数，提交后再通知相应前端。状态栏重绘只读这个计数。首次订阅或断线重连时从已提交状态取得快照，再接收后续更新。这样，从 1 个会话增加到 16 个会话时，写入 1 个任务仍只更新其所属会话的计数。

修改重复执行的路径时，作者应能说明谁触发工作、谁拥有源数据、一次变化会读写哪些对象，以及何时必须重新核验。评审时固定一次实际变更，分别增加历史量、无关订阅者或重复调用次数，检查哪项工作会随之增长。把其中最容易退化的一项写成真实入口的回归断言，同时确认目标用户收到正确结果。

发布前核对受影响的预算和结果。次数可以稳定断言时，直接数查询、进程启动或通知。主要成本在计算时，用同一环境和负载重复比较 CPU 时间与用户可见延迟。超出已接受预算或漏掉必要更新的变更，应先修复。确需调整预算时，在同一 PR 中记录用户收益、实测代价和新上限。[性能预算及运行方法](../../scripts/performance/README.md)
