# Make Pi lifecycle follow session ownership

Recommend extending Pi’s existing connection path to ensure a compatible daemon on demand, with session expiry and empty-daemon shutdown owned by that daemon. **24 hours of session inactivity and 30 minutes with zero active sessions are requested Pi defaults, not VS Code facts.** The human has confirmed that all idle sessions, including attached ones, can expire by closing their runtime while retaining reopenable history. Genuinely executing model, tool, and session-owned background work must remain protected without output, with inactivity beginning when work finishes. These confirmations override ambiguities in the completed notes. This report recommends architecture, not an approved implementation specification; all other policy choices below remain recommendations for human acceptance ([requirements](../research_notes/Remote%20server%20lifecycle%20policy/requirements.md)).

## VS Code separates consumer lifetime from reconnection

Official documentation says Remote-SSH automatically installs/updates its server and manages startup/shutdown without login or boot scripts ([FAQ](https://code.visualstudio.com/docs/remote/faq.md)). Historical June 2019 maintainer comments describe reusing a running server and a `/delay-shutdown` handshake spanning the connect/shutdown race ([maintainer](https://github.com/microsoft/vscode-remote-release/issues/203#issuecomment-503239644)). These are historical integration statements; the **closed-source current Remote-SSH resolver’s** exact probes, locks, retries, and reboot recovery remain unverified ([source availability](https://code.visualstudio.com/docs/remote/faq.md#why-arent-the-remote-development-extensions-or-their-components-open-source)).

Public upstream source pinned to **`caf4fe387393f704f7eb94578e48dcff65bf8032`**, a main-branch snapshot rather than a shipped-version guarantee, implements opt-in auto-shutdown after **five minutes with zero active consumers**. Consumers include extension hosts and certain agent-host activity; sockets alone are not the count. An additional option skips non-initial delays. Generation checks can cancel shutdown during cleanup ([lifetime service](https://github.com/microsoft/vscode/blob/caf4fe387393f704f7eb94578e48dcff65bf8032/src/vs/server/node/serverLifetimeService.ts), [agent-host consumers](https://github.com/microsoft/vscode/blob/caf4fe387393f704f7eb94578e48dcff65bf8032/src/vs/server/node/serverAgentHostManager.ts)).

Separately, disconnected connections have a default **three-hour reconnection grace**, configurable through a server CLI option and sometimes shortened on subsequent connectivity. This is neither last-user-activity expiry nor the empty-server timer ([protocol constants](https://github.com/microsoft/vscode/blob/caf4fe387393f704f7eb94578e48dcff65bf8032/src/vs/base/parts/ipc/common/ipc.net.ts#L301), [options](https://github.com/microsoft/vscode/blob/caf4fe387393f704f7eb94578e48dcff65bf8032/src/vs/server/node/serverEnvironmentService.ts), [disconnect handling](https://github.com/microsoft/vscode/blob/caf4fe387393f704f7eb94578e48dcff65bf8032/src/vs/workbench/api/node/extensionHostProcess.ts)). Pi should borrow the separation and race protection, not conflate these clocks or import Remote Tunnels/serve-web policy.

## Repair connection preparation within the existing path

The parent-verified incident supersedes the notes’ earlier “supplied repro” qualification: `node /private/tmp/pi-remote-r5.KrtGtk/src/remote-cli.ts ls --host 115 --json` returned `pi-remote: connection closed`, including with explicit `--remote-dir /home/exoulster/.pi-better-server-trial/state`. SSH `115` reached `r5`; uptime was 38 minutes, tmux was missing, no Pi listener existed, and the trial socket was stale. `115` selected the default directory while `r5` selected the trial directory. Deployed source advertised only `native-client-v1`/`package-sync-v1`, missing `session-browser-v1`. These observations establish absence and target/compatibility problems, not a 24-hour expiry failure. No recovery, profile, or code mutations occurred; nothing is claimed fixed.

Today `resolveTarget` discovers a directory and forwards its socket; `DaemonClient.connect` performs socket connection/hello. Neither starts the missing daemon. Startup can unlink stale sockets but lacks cross-process ownership; native connection separately rejects missing browser capability ([target](../../../packages/pi-better-server/src/remote/target.ts), [client](../../../packages/pi-better-server/src/client.ts), [server](../../../packages/pi-better-server/src/server.ts), [native client](../../../packages/pi-better-server/src/remote-client/extension.ts)).

Recommend one shared connection-preparation boundary used by native and CLI callers: **resolve identity → ensure health → serialize startup of an installed compatible daemon if absent → readiness/hello → forward/attach**. Readiness/hello can use a temporary transport; normal forwarding and attachment proceed only against the verified endpoint. Keep `DaemonClient` transport-focused, reuse existing SSH facilities and daemon entrypoint, and avoid a second execution service. The trade-off is coordinated lifecycle complexity in exchange for consistent recovery across callers; an always-running supervisor adds boot policy unnecessary for on-demand startup. Launch must survive the requesting SSH command’s exit.

Identity must include remote account/host, canonical configured `serverDir`, and agent kind. Resolve profiles and explicit directory selection consistently before probing or launching; show the effective directory in diagnostics. For aliases such as `115`/`r5`, detect conflicting directory selections before automatic startup and require deliberate target selection. Distinct directories remain valid deliberate instances, but alias drift must not silently create two daemons ([profiles](../../../packages/pi-better-server/src/remote-client/profiles.ts), [path conventions](../../../packages/pi-better-server/src/paths.ts)).

A socket file never establishes liveness. Under a per-directory startup claim, recheck process ownership and protocol health before stale cleanup. Reuse healthy compatible daemons. SSH failure must not trigger blind restart; incompatibility requires a safe upgrade workflow, never killing a busy daemon. Missing runtime needs actionable bootstrap guidance and may require installation approval. Bound startup waiting and return stage-specific failure rather than bare “connection closed.”

## Keep lifecycle authority beside the existing registry

Recommend registry-owned session lifecycle and persisted meaningful-activity timestamps, with daemon-owned clocks throughout. `HostedSession` should expose execution ownership and settlement to the registry; server lifetime should consume the registry’s authoritative open-session count. Existing `running` means resumable/open, `updatedAt` includes metadata, and `isStreaming` misses some in-flight work. Existing close/reopen already preserves transcripts; in-process session serialization can carry expiry, but does not solve daemon startup races ([registry](../../../packages/pi-better-server/src/registry.ts), [hosted session](../../../packages/pi-better-server/src/hosted-session.ts), [code map](../research_notes/Remote%20server%20lifecycle%20policy/pi.md)).

| State | Recommended lifetime treatment |
| --- | --- |
| Open, executing | Active; protect silent model/tool/owned background work. |
| Open, idle or needs input | Active until inactivity expiry, even when attached. Waiting is not execution. |
| Closed/expired | No runtime; retained history; explicit reopen. |
| Daemon with zero open sessions | Start 30-minute window; passive clients do not extend it. |
| Starting/draining | Brief bounded startup leases and ownership fencing coordinate admission. |

“Active” should mean open and owned here, not attached or currently generating. Exclude moved/fenced ownership; failed restoration must remain visibly unresolved rather than silently closed or incorrectly hosted. Background protection requires observable session ownership, completion/cancellation signals, and reconciliation after restart. Unknown external processes cannot receive this guarantee. Never-ending owned work can therefore keep the daemon alive indefinitely, a deliberate consequence of the confirmed protection.

Recommend creation/reopen, accepted user actions, and explicit attach as qualifying activity; polls, heartbeat, passive viewing, automatic reconnect, and rename do not reset expiry. Start a full window when the last execution finishes or yields to input. Serialize accepted activity against expiry: closure winning requires explicit reopen. Expiry invalidates pending approvals; reopening must neither approve nor silently replay them.

Persist session inactivity meaning across restart, counting offline time for idle sessions. Reconcile execution before expiry; a persisted busy flag alone proves nothing. Recommend a fresh window when interruption is established, without replaying interrupted tools. Expiry preserves history and uses close semantics, while crash recovery restores context only ([documented recovery](../../../packages/pi-better-server/README.md)).

Use an exclusive daemon ownership claim plus generation-based shutdown fencing. Before final exit, recheck zero sessions, startup leases, and accepted create/open operations. Once draining commits, reject admission explicitly; callers can retry through the same ensure path after ownership release. Leases expire promptly and cannot renew session activity. Start the zero-session clock when readiness first finds zero or the last session closes; a new open session cancels it. Recommend a fresh daemon idle window after restart. Intentional idle shutdown must leave passive clients stopped until deliberate demand, avoiding eager reconnect loops.

## Validate boundaries before approving user-visible policy

Configuration should expose two independent conceptual durations, defaulting to 24h and 30m, resolved once for each daemon identity through its existing launch/options boundary. No existing keys are asserted. Before implementation, define precedence, scope, disabled/zero behavior, changes to running deadlines, attach activity, interruption grace, and manual close while busy. This report does not replace current manual-close behavior.

Acceptance tests should cover concurrent first connects converging on one writer; stale-socket crash/reboot recovery without tool replay; silent execution beyond 24h with expiry only after a subsequent full idle window; attached idle expiry and history reopen without stale approval reuse; and 30 continuous zero-session minutes despite polling. Race cases must cover expiry versus accepted activity and shutdown versus create/reopen, preserving accepted work or returning an explicit retry outcome. Failure scenarios should distinguish SSH/authentication, target ambiguity, permission, missing runtime, incompatible capabilities, startup failure, and readiness timeout, identifying target and corrective next step without destructive recovery.

**No decision blocks this research report.** Before implementation, settle configuration semantics, execution/background ownership signals, and launch survival/platform constraints. The key architectural cost is durable ownership coordination, which prevents convenience recovery from creating duplicate writers or interrupting real work.
