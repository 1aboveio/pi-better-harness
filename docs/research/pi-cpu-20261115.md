# Navigator detail CPU investigation, 2026-11-15

## Confirmed defect

Harness 0.46.0 still reads providers from the detail overlay's `render()`:

```text
detail overlay render
  refreshRows
    listRows
      subagentWorkRows
        sessionVisibleNavigatorRuns
          isExpiredTerminalNavigatorRun
            assignment projection
              readAssignmentWaits
                open read-only SQLite connection
```

Streaming output, mouse hover and other unrelated paints therefore repeat task
observations. The previous paint budget covered the main list, whose render
already uses a snapshot, but did not open the detail overlay. #749 shares an
observation within one provider refresh; it does not bound the refresh frequency.

## Live observations

- A 10-second cumulative CPU-time measurement found one Pi process averaging
  66.2% and another averaging 11.4%. Activity state was not controlled.
- A 5.27-second filesystem trace of the first process recorded 9,464 opens of
  the coordinator WAL file and roughly 453,000 filesystem events. WAL opens are
  filesystem observations, not a count of JavaScript `DatabaseSync` constructors.
- That session's origin index contained 107 attempts: 106 completed and one
  running. Of these, 105 had ended at least 30 seconds earlier.
- Another process performed 97,031 historical session-state stats in 3.13 seconds;
  94,959 returned missing-file errors. Only 31 marker files existed on disk.
- The installed Harness was 0.46.0 and contained the #747 and #749 fixes. The
  exact code loaded in existing processes could not be established. Process age
  alone does not establish an extension version or whether it was reloaded.
- `fseventsd` also consumed about one CPU core. Other sessions were running disk
  scans. These are separate contributors to machine load.
- A final unprofiled 10-second measurement found another Pi process averaging
  99.2%. Its subsequent 2.11-second trace recorded 48,005 run-metadata opens and
  945 coordinator WAL opens. A native sample placed most main-thread samples
  under timer callbacks. This is a distinct batch-reading pattern; the loaded
  JavaScript version and exact timer could not be identified from native frames.

Native samples contained synchronous SQLite/filesystem work and incoming TLS
callbacks. An existing debugger occupied port 9229, so no inspector was attached
to the user processes. No user session was stopped or reloaded.

## Controlled reproduction

Fresh private tmux sessions ran Pi 1.5.2 on Node 24.21.0, with isolated home,
agent, temporary, durable-history and session directories. They loaded the actual
Goal, Background Tasks and Subagents extensions, created 107 owned attempts
(106 completed 40 seconds ago, one running), and requested 60 paints per second.
No model request was made. The detail overlay was opened through Left and Enter.

SQLite constructor and metadata-read counters were injected before extension
loading. Stack collection was disabled for the following CPU comparison. Startup
windows are excluded; each reported window lasted approximately five seconds.

| Detail overlay | CPU | SQLite opens per five seconds |
| --- | --- | --- |
| Published 0.46.0 | 91.7%-96.3% | 17,548-19,688 |
| Patched source | 10.0%-14.9% | 535 in stable windows |

The first patched post-startup window had 1,070 opens. Subsequent windows had
535, matching one full 107-attempt observation per second. This remaining
history-dependent polling cost belongs to the shared observation work in #753;
the present change removes its multiplication by paint frequency.

The controlled result proves the released detail-overlay defect. It does not
attribute every live process's CPU to that defect.

## Fix and regression evidence

Detail paints now consume the main list's existing `mainListRows` snapshot.
Provider notifications and the existing refresh deadline keep the snapshot
current. Keyboard and pointer command paths retain their explicit reads.

The added unit test failed before the fix: 60 unchanged detail paints caused
60 additional provider calls. The performance scenario failed with one row:
60 provider calls, 60 metadata reads and 60 SQLite opens, against zero budgets.

```sh
node --import tsx --test packages/navigator/index.test.ts packages/navigator/panels.test.ts
node --import tsx scripts/performance/assignment-projection-stress.mjs
npm run typecheck -w navigator -w pi-better-background-tasks
```

After the fix, all 42 Navigator tests and all 36 performance scenarios passed.
The nine added overlay scenarios cover 1, 20 and 50 rows with 200, 1,000 and
2,000 registry records. Each requires zero provider calls, metadata reads and
SQLite opens for 60 unchanged paints. The unit test also checks timer-based
external updates, provider notifications and disposal.

Six real-terminal journeys passed: Unicode navigation, pointer selection,
closing work, refocusing a reused overlay, replacing the editor and wrapping
the editor. The initial run could not load an unstaged model-router dependency;
staging the bundle dependencies resolved that setup failure.

Raw live traces and controlled-run metrics remain in local `/tmp/pi-cpu-20261115-*`
diagnostic artifacts. No user state, installed package or global setting was changed.
The patch is separate from the installed release and does not update existing
user processes.
