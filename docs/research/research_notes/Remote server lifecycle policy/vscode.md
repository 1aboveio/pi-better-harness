# VS Code Remote-SSH Server Lifecycle Evidence

## 1. Does Remote-SSH install, start, and reuse its server automatically?

### Takeaway
Official documentation establishes client-managed automatic installation/update and start/stop, without login/startup scripts. Maintainer statements establish checking for and reusing an already-running server; public server source does not expose the complete current Remote-SSH resolver implementation. [Official FAQ](https://code.visualstudio.com/docs/remote/faq.md); [maintainer explanation, 2019-06-07](https://github.com/microsoft/vscode-remote-release/issues/203#issuecomment-500002309).

### Cited Findings
- **Source snapshot:** researched 2026-10-19 UTC. GitHub's `commits/main` API returned `caf4fe387393f704f7eb94578e48dcff65bf8032`, committed 2026-10-19T14:29:23Z. All upstream implementation links below pin that exact revision; it is a main-branch snapshot, not a claim about the currently installed stable release or a particular Remote-SSH extension version. [Commit API](https://api.github.com/repos/microsoft/vscode/commits/caf4fe387393f704f7eb94578e48dcff65bf8032).
- Remote-SSH installs VS Code Server on the remote OS, independently of an existing VS Code installation there; connecting makes VS Code connect and set itself up. The FAQ says the server is installed and updated automatically when VS Code connects to an endpoint. [Remote-SSH documentation](https://code.visualstudio.com/docs/remote/ssh); [FAQ: server installation](https://code.visualstudio.com/docs/remote/faq.md#can-vs-code-server-be-installed-or-used-on-its-own).
- The injected server runs as the login user. Exact FAQ wording: "The server is started and stopped by VS Code and is not wired into any user or global login or startup scripts. VS Code manages the server's lifecycle so you do not need to worry about whether or not it is running." This supports client-managed startup, not automatic boot-time resurrection. [FAQ: securing access](https://code.visualstudio.com/docs/remote/faq.md#how-do-the-remote-development-extensions-secure-access-to-a-remote-machine-vm-or-container).
- In June 2019, maintainer `roblourens` explained that a connecting window determines whether the server is already running or needs starting, then asks it to create an extension host. He later described the resolver wanting to connect to a running server and the need to verify that it is not shutting down. These are direct primary-source statements of start-or-reuse intent, but historical rather than a current resolver-code audit. [2019-06-07](https://github.com/microsoft/vscode-remote-release/issues/203#issuecomment-500002309); [2019-06-17](https://github.com/microsoft/vscode-remote-release/issues/203#issuecomment-502758078); [2019-06-18](https://github.com/microsoft/vscode-remote-release/issues/203#issuecomment-502900161).
- Reuse of an installed/running server is distinct from resuming an extension-host connection. Current server source keeps reconnection tokens and connection objects in memory, accepts reconnections to known connections, rejects unknown/expired tokens, and rejects client/server commit mismatches when both commits are defined. [Pinned remoteExtensionHostAgentServer.ts](https://github.com/microsoft/vscode/blob/caf4fe387393f704f7eb94578e48dcff65bf8032/src/vs/server/node/remoteExtensionHostAgentServer.ts).
- Closing the remote connection is documented through `File > Close Remote Connection` or exiting VS Code. That documentation does not specify a server-process shutdown deadline. [Remote-SSH: disconnect](https://code.visualstudio.com/docs/remote/ssh#disconnect-from-a-remote-host).

### Inferences
- The documented lifecycle is on-connect client management, not a requirement that users pre-start the injected server. This does not establish the exact recovery sequence for a stale Unix socket after reboot. [FAQ lifecycle description](https://code.visualstudio.com/docs/remote/faq.md#how-do-the-remote-development-extensions-secure-access-to-a-remote-machine-vm-or-container).
- Because extension-host reconnection objects are in memory, those particular objects cannot survive replacement of the server process; reuse of downloaded server files must not be described as preservation of live reconnection state across reboot. [Pinned connection bookkeeping](https://github.com/microsoft/vscode/blob/caf4fe387393f704f7eb94578e48dcff65bf8032/src/vs/server/node/remoteExtensionHostAgentServer.ts).

### Gaps
- Exact present-day resolver liveness probes, PID/socket validation, stale socket deletion, bootstrap locking, retries, and reboot recovery were not verified. The official FAQ explicitly says Remote Development extensions and related components are not currently open source; public VS Code server code is not the closed-source Remote-SSH resolver. [FAQ: source availability](https://code.visualstudio.com/docs/remote/faq.md#why-arent-the-remote-development-extensions-or-their-components-open-source).
- No specific shipped VS Code/Remote-SSH version or live connection log was supplied or tested. Main-branch behavior below must not be silently promoted into a guarantee for every released extension/build.

## 2. When does the server shut down, and how is the connect/shutdown race handled?

### Takeaway
The current public server has opt-in auto-shutdown, with a **five-minute** no-active-consumer delay, and an option to skip that delay on non-initial shutdowns. Historical descriptions focus on zero extension hosts; current upstream generalizes the condition to zero active consumers, including certain agent-host consumers. `/delay-shutdown` remains the explicit startup-race mitigation mechanism. [Pinned lifetime service](https://github.com/microsoft/vscode/blob/caf4fe387393f704f7eb94578e48dcff65bf8032/src/vs/server/node/serverLifetimeService.ts); [pinned agent-host manager](https://github.com/microsoft/vscode/blob/caf4fe387393f704f7eb94578e48dcff65bf8032/src/vs/server/node/serverAgentHostManager.ts); [maintainer handshake contract](https://github.com/microsoft/vscode-remote-release/issues/203#issuecomment-503239644).

### Cited Findings
- **Opt-in, not unconditional:** `serverOptions` declares Boolean `--enable-remote-auto-shutdown` and `--remote-auto-shutdown-without-delay`. `serverServices.ts` passes their Boolean values into `ServerLifetimeService` as `enableAutoShutdown` and `shutdownWithoutDelay`. Without enablement, the service does not schedule automatic shutdown. [Pinned option declarations](https://github.com/microsoft/vscode/blob/caf4fe387393f704f7eb94578e48dcff65bf8032/src/vs/server/node/serverEnvironmentService.ts); [pinned service construction](https://github.com/microsoft/vscode/blob/caf4fe387393f704f7eb94578e48dcff65bf8032/src/vs/server/node/serverServices.ts); [pinned lifetime behavior](https://github.com/microsoft/vscode/blob/caf4fe387393f704f7eb94578e48dcff65bf8032/src/vs/server/node/serverLifetimeService.ts).
- **Delay:** `SHUTDOWN_TIMEOUT = 5 * 60 * 1000` milliseconds. With auto-shutdown enabled, construction schedules an initial timer with no clients yet; the first consumer cancels it; disposing the last active consumer schedules shutdown again. The service checks that no consumers exist before requesting shutdown and exiting with code 0. [Pinned ServerLifetimeService](https://github.com/microsoft/vscode/blob/caf4fe387393f704f7eb94578e48dcff65bf8032/src/vs/server/node/serverLifetimeService.ts).
- **Immediate option qualification:** `shutdownWithoutDelay && !initial` invokes shutdown without the five-minute timer. Initial startup still gets the timer. `delay()` reschedules with `initial=false`, so the without-delay option also affects that rescheduling path; it is not an unconditional promise that every delay request buys five minutes. [Pinned scheduling and delay methods](https://github.com/microsoft/vscode/blob/caf4fe387393f704f7eb94578e48dcff65bf8032/src/vs/server/node/serverLifetimeService.ts).
- **Extension-host counting:** a fresh extension-host connection acquires `active('ExtensionHost:...')`; closing it deletes and disposes its lifetime token. Management connections in the same server file do not acquire that token. [Pinned connection registration/close handling](https://github.com/microsoft/vscode/blob/caf4fe387393f704f7eb94578e48dcff65bf8032/src/vs/server/node/remoteExtensionHostAgentServer.ts).
- **Current zero-EH qualification:** the lifetime service counts active consumers, not merely extension hosts. `ServerAgentHostManager` also holds an `AgentHost` lifetime token while it reports active agent sessions or connected standalone WebSocket clients; renderer-to-agent-host proxy connections are explicitly excluded from that manager's counting. Thus zero extension hosts alone need not be sufficient to shut down the current shared server in configurations using these consumers. [Pinned lifetime API](https://github.com/microsoft/vscode/blob/caf4fe387393f704f7eb94578e48dcff65bf8032/src/vs/server/node/serverLifetimeService.ts); [pinned agent-host lifetime tracking](https://github.com/microsoft/vscode/blob/caf4fe387393f704f7eb94578e48dcff65bf8032/src/vs/server/node/serverAgentHostManager.ts).
- **Race rationale, historical primary source:** on 2019-06-07/17, the maintainer explained that the server can disappear between the resolver's running-process check and the later extension-host request. A lock-file proposal was discussed, then superseded by communicating with the server. On 2019-06-18 he specified two resolver obligations: launch with `--enable-remote-auto-shutdown`, then hit `/delay-shutdown` during connect so the timeout spans the gap before VS Code requests an extension host. The proposed lock-file design is not evidence of the implemented mechanism. [Initial proposal](https://github.com/microsoft/vscode-remote-release/issues/203#issuecomment-500002309); [race analysis](https://github.com/microsoft/vscode-remote-release/issues/203#issuecomment-502758078); [explicit handshake contract](https://github.com/microsoft/vscode-remote-release/issues/203#issuecomment-503239644).
- **Current implementation of mitigation:** a GET to `/delay-shutdown` calls the lifetime service's `delay()` and returns HTTP 200 `OK`. `delay()` increments a generation counter and resets an outstanding timer. If shutdown has entered asynchronous participant cleanup, a changed generation or newly active consumer aborts the pending exit; an abort event fires and, when still empty and auto-shutdown enabled, shutdown is rescheduled. The acknowledgement establishes that a live server handled the delay, not a guarantee against crashes or later exit. [Pinned HTTP endpoint](https://github.com/microsoft/vscode/blob/caf4fe387393f704f7eb94578e48dcff65bf8032/src/vs/server/node/remoteExtensionHostAgentServer.ts); [pinned generation/abort logic](https://github.com/microsoft/vscode/blob/caf4fe387393f704f7eb94578e48dcff65bf8032/src/vs/server/node/serverLifetimeService.ts).
- **Historical statements are date-sensitive:** May 2019 comments said the agent stays running to wait for requests. June 2019 comments introduced no-extension-host shutdown and opt-in resolver support. The earlier statement must not be cited as the current universal behavior. [2019-05-08](https://github.com/microsoft/vscode-remote-release/issues/203#issuecomment-490323291); [2019-05-30](https://github.com/microsoft/vscode-remote-release/issues/203#issuecomment-497402196); [2019-06-18](https://github.com/microsoft/vscode-remote-release/issues/203#issuecomment-503239644).

### Inferences
- For the extension-host-only case with auto-shutdown enabled, no without-delay option, and no additional delay requests, the source supports five minutes after the last extension-host lifetime token is released, not necessarily five minutes after a client network socket drops. The token belongs to the extension-host connection lifecycle, which can outlast transport loss. [Pinned connection lifetime tokens](https://github.com/microsoft/vscode/blob/caf4fe387393f704f7eb94578e48dcff65bf8032/src/vs/server/node/remoteExtensionHostAgentServer.ts); [pinned extension-host reconnection timers](https://github.com/microsoft/vscode/blob/caf4fe387393f704f7eb94578e48dcff65bf8032/src/vs/workbench/api/node/extensionHostProcess.ts).

### Gaps
- The reviewed public option definitions expose enablement and immediate/non-immediate selection, not a numeric zero-consumer shutdown-delay option; the five-minute value is a source constant. This is not proof that no proprietary Remote-SSH setting, wrapper, or experimental configuration can affect behavior. [Pinned options](https://github.com/microsoft/vscode/blob/caf4fe387393f704f7eb94578e48dcff65bf8032/src/vs/server/node/serverEnvironmentService.ts); [pinned constant](https://github.com/microsoft/vscode/blob/caf4fe387393f704f7eb94578e48dcff65bf8032/src/vs/server/node/serverLifetimeService.ts).
- Whether a particular current Remote-SSH mode/version supplies either flag, uses this endpoint, or overrides launch arguments cannot be established from these public server files alone. Maintainer statements specify the historical integration contract; the resolver remains closed source. [Maintainer contract](https://github.com/microsoft/vscode-remote-release/issues/203#issuecomment-503239644); [official source-availability limitation](https://code.visualstudio.com/docs/remote/faq.md#why-arent-the-remote-development-extensions-or-their-components-open-source).

## 3. What are the reconnection defaults and product boundaries?

### Takeaway
Current upstream distinguishes a **three-hour disconnected-connection reconnection grace** from the **five-minute zero-consumer shutdown delay**. Neither is a 24-hour last-user-activity session expiry or a 30-minute daemon-idle default. Shared backend technology does not make Remote-SSH, `code tunnel`, and `code serve-web` lifecycle policies interchangeable. [Pinned protocol constants](https://github.com/microsoft/vscode/blob/caf4fe387393f704f7eb94578e48dcff65bf8032/src/vs/base/parts/ipc/common/ipc.net.ts); [pinned lifetime service](https://github.com/microsoft/vscode/blob/caf4fe387393f704f7eb94578e48dcff65bf8032/src/vs/server/node/serverLifetimeService.ts); [official Server overview](https://code.visualstudio.com/docs/remote/vscode-server.md).

### Cited Findings
- **Long reconnection grace:** `ProtocolConstants.ReconnectionGraceTime = 3 * 60 * 60 * 1000` ms. The accompanying comment says that without reconnection in that time frame, consider the connection permanently closed. `ReconnectionShortGraceTime = 5 * 60 * 1000` ms is a separate short-grace constant. [Pinned ipc.net.ts](https://github.com/microsoft/vscode/blob/caf4fe387393f704f7eb94578e48dcff65bf8032/src/vs/base/parts/ipc/common/ipc.net.ts#L301).
- **Numeric configurability:** `--reconnection-grace-time <seconds>` is a declared server CLI option, described as defaulting to `10800 (3 hours)`. The environment service converts finite nonnegative seconds to floored milliseconds; missing/blank, negative, nonfinite, or excessively large values fall back to the protocol default. Zero is accepted. This is a server CLI capability, not evidence of a corresponding supported Remote-SSH user setting. [Pinned serverEnvironmentService.ts](https://github.com/microsoft/vscode/blob/caf4fe387393f704f7eb94578e48dcff65bf8032/src/vs/server/node/serverEnvironmentService.ts).
- The server passes the configured value to management connections and into extension-host environment variable `VSCODE_RECONNECTION_GRACE_TIME` in milliseconds. The extension-host process starts its long termination scheduler when its protocol socket closes and cancels disconnect schedulers when a socket reconnects. Protocol disposal terminates the extension host without treating it as a recoverable socket interruption. [Pinned server connection construction](https://github.com/microsoft/vscode/blob/caf4fe387393f704f7eb94578e48dcff65bf8032/src/vs/server/node/remoteExtensionHostAgentServer.ts); [pinned environment propagation](https://github.com/microsoft/vscode/blob/caf4fe387393f704f7eb94578e48dcff65bf8032/src/vs/server/node/extensionHostConnection.ts); [pinned extension-host protocol/timers](https://github.com/microsoft/vscode/blob/caf4fe387393f704f7eb94578e48dcff65bf8032/src/vs/workbench/api/node/extensionHostProcess.ts).
- A new authenticated connection causes the server to request shorter grace for other disconnected connections because it indicates the owner has connectivity. The extension-host process schedules the short timer only if its long disconnect timer is scheduled; short grace is `min(5 minutes, configured long grace)` for positive long grace, otherwise zero. Thus three hours is not an unconditional minimum retention guarantee. [Pinned server handshake](https://github.com/microsoft/vscode/blob/caf4fe387393f704f7eb94578e48dcff65bf8032/src/vs/server/node/remoteExtensionHostAgentServer.ts); [pinned shortening logic](https://github.com/microsoft/vscode/blob/caf4fe387393f704f7eb94578e48dcff65bf8032/src/vs/workbench/api/node/extensionHostProcess.ts).
- **Not last-activity expiry:** the reviewed extension-host grace is triggered by transport socket closure; the server shutdown timer is triggered by having no active consumers. These are not definitions of a session expiring after a period without new prompts, edits, or other user activity. [Pinned disconnect scheduler](https://github.com/microsoft/vscode/blob/caf4fe387393f704f7eb94578e48dcff65bf8032/src/vs/workbench/api/node/extensionHostProcess.ts); [pinned consumer-based timer](https://github.com/microsoft/vscode/blob/caf4fe387393f704f7eb94578e48dcff65bf8032/src/vs/server/node/serverLifetimeService.ts).
- **Remote-SSH:** official documentation describes an SSH-server prerequisite and an extension-managed remote backend; the FAQ describes authenticated SSH tunnels and client-managed lifecycle without startup scripts. [SSH documentation](https://code.visualstudio.com/docs/remote/ssh); [Remote Development FAQ](https://code.visualstudio.com/docs/remote/faq.md).
- **Standalone VS Code Server / Remote Tunnels:** the Server overview explicitly distinguishes a standalone service built on the same underlying remote-extension server, adding an interactive CLI and vscode.dev connections without requiring SSH. Tunnels docs say `code tunnel` downloads/starts the backend and creates a tunnel. They document `code tunnel service install` / `uninstall` for keeping the tunnel running, and Ctrl+C to end a foreground CLI tunnel. Those are tunnel lifecycle facts, not Remote-SSH boot/liveness policy. [Server overview](https://code.visualstudio.com/docs/remote/vscode-server.md); [Remote Tunnels documentation](https://code.visualstudio.com/docs/remote/tunnels.md).
- **`code serve-web`:** the separate Rust command implements a browser-facing "server of servers," with per-version connection reference counts. Its `SERVER_IDLE_TIMEOUT_SECS = 60 * 60` is one hour for server children with no connections, and its own timeout handling kills the child process tree. This separate supervisor's timeout is not the Remote-SSH no-extension-host shutdown default and is not proof the serve-web frontend itself exits after one hour. [Pinned serve_web.rs](https://github.com/microsoft/vscode/blob/caf4fe387393f704f7eb94578e48dcff65bf8032/cli/src/commands/serve_web.rs).

### Inferences
- A disconnected extension host can continue holding the server alive during reconnection grace; only after its lifecycle closes can its lifetime token be released and the no-consumer shutdown mechanism take effect, provided no other consumers remain. This distinguishes two stages rather than treating three hours and five minutes as conflicting descriptions of one timer. [Pinned extension-host close/lifetime-token handling](https://github.com/microsoft/vscode/blob/caf4fe387393f704f7eb94578e48dcff65bf8032/src/vs/server/node/remoteExtensionHostAgentServer.ts); [pinned extension-host termination timer](https://github.com/microsoft/vscode/blob/caf4fe387393f704f7eb94578e48dcff65bf8032/src/vs/workbench/api/node/extensionHostProcess.ts).

### Gaps
- No evidence in the cited lifecycle sources establishes **24 hours of no new activity** as a VS Code session default or **30 minutes with zero sessions** as a VS Code daemon default. Do not attribute those proposal values to VS Code; the verified upstream values concern different predicates and are three hours / five minutes as qualified above. [Pinned reconnection default](https://github.com/microsoft/vscode/blob/caf4fe387393f704f7eb94578e48dcff65bf8032/src/vs/base/parts/ipc/common/ipc.net.ts#L301); [pinned shutdown default](https://github.com/microsoft/vscode/blob/caf4fe387393f704f7eb94578e48dcff65bf8032/src/vs/server/node/serverLifetimeService.ts).
- Official pages have a product-scope/documentation tension: the Remote Development FAQ says its injected server is not intended for separate installation, whereas the standalone Server overview describes that separate product; the Server overview also says hosting as a service is not allowed, while Tunnels docs explicitly document installing a tunnel service. Record these as differently scoped/inconsistent documentation, not grounds to infer a uniform lifecycle or licensing rule. No product or licensing policy is selected here. [Remote Development FAQ](https://code.visualstudio.com/docs/remote/faq.md); [Server overview](https://code.visualstudio.com/docs/remote/vscode-server.md); [Tunnels service instructions](https://code.visualstudio.com/docs/remote/tunnels.md#how-can-i-ensure-i-keep-my-tunnel-running).
- This note verifies external VS Code evidence only. It does not examine Pi repository execution paths, choose Pi retention semantics, or prescribe implementation.
