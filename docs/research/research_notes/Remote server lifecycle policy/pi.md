# Pi Remote Daemon and Session Lifecycle Policy Map

## Connection path, target resolution, and startup

### Takeaway
`resolveTarget` is a transport resolver, not a daemon manager: local mode returns a socket path, while SSH mode discovers/selects the remote server directory and forwards its Unix socket. Neither path starts a daemon when absent. `startDaemon` can remove a stale socket and resume registry entries, but startup currently has no cross-process lock around stale-socket removal, resume, and `listen`.

### Cited Findings
- Local target resolution chooses `options.socket` or `socketPathFor(defaultServerDir())`; remote resolution sets up SSH, resolves `remoteDir` (explicit value, `PI_REMOTE_SERVER_DIR`, or remote shell default), then forwards `pi-server.sock`. No daemon-start command is issued in this path. — [target.ts](/Users/exoulster/projects/pi-better-harness/packages/pi-better-server/src/remote/target.ts:37)
- `DaemonClient.connect` connects to the supplied Unix socket and performs `hello`; it only knows the path and has no target/start operation. — [client.ts](/Users/exoulster/projects/pi-better-harness/packages/pi-better-server/src/client.ts:47)
- Native `/remote` calls `resolveTarget`, connects, then checks `native-client-v1` and `session-browser-v1`. An older server missing the latter is explicitly rejected before local runtime replacement. — [extension.ts](/Users/exoulster/projects/pi-better-harness/packages/pi-better-server/src/remote-client/extension.ts:103)
- The CLI starts the selected Pi/Codex daemon in the foreground and only hooks SIGINT/SIGTERM for graceful stop. It does not daemonize itself or install a supervisor. — [cli.ts](/Users/exoulster/projects/pi-better-harness/packages/pi-better-server/src/cli.ts:16)
- `startDaemon` ensures the private server directory, probes an existing socket, errors if it is live, and unlinks it if the probe fails. It resumes indexed sessions before binding the socket. No lock file, pid ownership token, or atomic startup claim is present in this sequence. — [server.ts](/Users/exoulster/projects/pi-better-harness/packages/pi-better-server/src/server.ts:44)
- Socket path is `pi-server.sock` under the server directory; default directory is `$PI_SERVER_DIR` or the Pi agent directory's `server` child. Directory permissions are enforced as 0700 and socket mode is 0600. — [paths.ts](/Users/exoulster/projects/pi-better-harness/packages/pi-better-server/src/paths.ts:6)
- The live-socket probe and subsequent unlink are separate operations. Two concurrent starters can both observe an absent/stale socket and race through registry resume and listen; OS bind may reject one, but there is no explicit lock coordinating resume/index writes. Registry persistence uses a PID-suffixed temp file followed by rename, which is atomic for each write but not a cross-process ownership mechanism. — [server.ts](/Users/exoulster/projects/pi-better-harness/packages/pi-better-server/src/server.ts:32), [registry.ts](/Users/exoulster/projects/pi-better-harness/packages/pi-better-server/src/registry.ts:376)
- Supplied repro (not independently verified by repository code): SSH alias `r5` resolves to server dir `/home/exoulster/.pi-better-server-trial/state`, while the remote default differs; host reboot was about 38 minutes earlier; no Pi listening socket was present, a trial socket file was stale, and tmux was absent. The saved `r5` profile can select that trial path. No remote inspection or operation was performed for this assignment.

### Inferences
- “Auto-start on first connect” requires a remote launch path in addition to socket forwarding. A transport-level socket failure alone cannot safely distinguish absent daemon from SSH failure, profile path mismatch, incompatible server, permission failure, or startup-in-progress.
- The existing stale-socket guard addresses post-crash filesystem residue only after an explicit local `startDaemon`; it is not a complete concurrent start/stop protocol. Concurrent first-connect clients would need a single-writer claim and readiness/handshake coordination to avoid duplicate launch and half-start races.
- `resolveTarget` default path and remembered remote profile are independent selectors. The saved profile is consumed by the native extension before target resolution; remote CLI tools use their own options/environment/default behavior. Policies and diagnostics must preserve which `serverDir` was actually selected rather than assuming one host maps to one directory. — [profiles.ts](/Users/exoulster/projects/pi-better-harness/packages/pi-better-server/src/remote-client/profiles.ts:17), [target.ts](/Users/exoulster/projects/pi-better-harness/packages/pi-better-server/src/remote/target.ts:70)

### Gaps
- There is no implementation-defined launcher contract, service manager integration, readiness timeout/retry policy, or explicit “start if absent” behavior in the explored Pi client path.
- No lock or ownership protocol currently protects cross-process daemon startup, shutdown, or `sessions.json` mutation. The appropriate boundary/mechanism is an Architect decision; its implementation belongs to Developer.
- Whether auto-start applies only to native `/remote`, all `pi-remote` commands, local clients, or some subset is not determined by the current code.

## Registry state, activity, close/reopen, and crash recovery

### Takeaway
The persisted registry distinguishes `running` from `closed`; `running` means “resume this session after daemon restart,” not “actively generating.” `updatedAt` is refreshed by hosted-session callbacks and some metadata changes, but is not a daemon heartbeat and does not by itself encode user activity, attach time, pending input, or daemon idleness.

### Cited Findings
- `sessions.json` stores version 1 entries with session id, cwd, transcript path, lifecycle status, optional name/model, and created/updated timestamps. Registry comments state that sessions remain running until explicitly closed and are recovered after even `kill -9`. Conversation content remains in ordinary Pi session JSONL files. — [registry.ts](/Users/exoulster/projects/pi-better-harness/packages/pi-better-server/src/registry.ts:13), [registry.ts](/Users/exoulster/projects/pi-better-harness/packages/pi-better-server/src/registry.ts:41)
- Startup `resumeAll` hosts every persisted `running` entry not fenced/moved by ownership state; errors are retained in memory and logged without changing its indexed status. — [registry.ts](/Users/exoulster/projects/pi-better-harness/packages/pi-better-server/src/registry.ts:68)
- `open` restores a closed/unhosted session and marks it running. `close` aborts/releases it, marks the index row closed, updates timestamp, and persists. `rename` changes name and updates timestamp; on a closed session it writes session-info metadata without hosting it. — [registry.ts](/Users/exoulster/projects/pi-better-harness/packages/pi-better-server/src/registry.ts:122), [registry.ts](/Users/exoulster/projects/pi-better-harness/packages/pi-better-server/src/registry.ts:171), [registry.ts](/Users/exoulster/projects/pi-better-harness/packages/pi-better-server/src/registry.ts:187)
- `updatedAt` is updated by `touch`, which persists the index and refreshes model/name metadata. A hosted session receives this callback from `HostedSession`; selected rename/create/close paths also update it. It is therefore not a purpose-built last-human-interaction timestamp. — [registry.ts](/Users/exoulster/projects/pi-better-harness/packages/pi-better-server/src/registry.ts:299), [registry.ts](/Users/exoulster/projects/pi-better-harness/packages/pi-better-server/src/registry.ts:333)
- Summary exposes persisted `status` alongside runtime `isStreaming`, `needsInput`, `hasController`, and `live`. Display status is derived separately: closed first, then needs-input, then streaming/running, else idle. — [registry.ts](/Users/exoulster/projects/pi-better-harness/packages/pi-better-server/src/registry.ts:344), [sessions.ts](/Users/exoulster/projects/pi-better-harness/packages/pi-better-server/src/remote/sessions.ts:7)
- Daemon start removes a stale socket, loads the index, and resumes sessions. A test explicitly verifies that `kill -9` leaves the socket and that a subsequent daemon resumes sessions from the last persisted entry. — [server.ts](/Users/exoulster/projects/pi-better-harness/packages/pi-better-server/src/server.ts:48), [daemon.test.ts](/Users/exoulster/projects/pi-better-harness/packages/pi-better-server/test/daemon.test.ts:163)
- Session-scoped lifecycle operations are serialized in-process (`open`, `rename`, `close`, `retire`, `release`, `forget`); release waits for in-flight starts and disposal before another host, preventing concurrent `EventLog` writers within this registry process. Existing tests cover open/close ordering races. — [registry.ts](/Users/exoulster/projects/pi-better-harness/packages/pi-better-server/src/registry.ts:155), [registry.ts](/Users/exoulster/projects/pi-better-harness/packages/pi-better-server/src/registry.ts:211), [registry-lifecycle.test.ts](/Users/exoulster/projects/pi-better-harness/packages/pi-better-server/test/registry-lifecycle.test.ts:17)
- `close` is a lifecycle operation, not transcript deletion: it disposes the hosted object and persists `closed`; reopening uses `SessionManager.open` on the existing session file when it exists. Daemon `shutdown` disposes live hosted sessions but leaves their index state unchanged for recovery. — [registry.ts](/Users/exoulster/projects/pi-better-harness/packages/pi-better-server/src/registry.ts:187), [registry.ts](/Users/exoulster/projects/pi-better-harness/packages/pi-better-server/src/registry.ts:273), [registry.ts](/Users/exoulster/projects/pi-better-harness/packages/pi-better-server/src/registry.ts:324)
- Index writes use temp-file-plus-rename; transcript data is not stored in `sessions.json`. This supports preserving conversation files through daemon shutdown/restart, but the code does not define retention/deletion for old session JSONL files. — [registry.ts](/Users/exoulster/projects/pi-better-harness/packages/pi-better-server/src/registry.ts:376), [README.md](/Users/exoulster/projects/pi-better-harness/packages/pi-better-server/README.md:7)

### Inferences
- A 24-hour session expiry cannot safely be implemented by treating every old `updatedAt` as idle: a pending extension dialog may need a user response despite no recent timestamp, and `needsInput` is runtime-only in the summary rather than persisted in the registry index. Likewise `isStreaming` can be false during Pi preflight while a prompt is already in flight; `HostedSession` has a separate `turnActive` concept for that window. — [hosted-session.ts](/Users/exoulster/projects/pi-better-harness/packages/pi-better-server/src/hosted-session.ts:55), [hosted-session.ts](/Users/exoulster/projects/pi-better-harness/packages/pi-better-server/src/hosted-session.ts:129)
- Expiring by `close` would intentionally abort active work and permanently change restart behavior to closed. That is observably different from releasing a session while preserving `running`, so the policy must specify the treatment of streaming turns, pending input, companion/controller leases, and whether expiry is terminal or only unloads the runtime.
- `updatedAt` may advance on metadata events such as rename and is not named/documented as “last interaction”; policy semantics should define which events refresh expiry (human prompt, tool/model events, attach, list/refresh, rename, queued prompt, dialog response, background work) rather than inheriting this field implicitly.
- Crash recovery preserves the indexed session set and transcript pointer, but can only resume state persisted by the Pi session manager. An idle-expiry implementation should not remove JSONL files or discard index/transcript references as a side effect unless retention is an explicit separate policy.

### Gaps
- No session expiration timer, idle session state, last-human-activity field, expiration marker, retention/garbage-collection policy, or configurable duration exists in `DaemonOptions`/`SessionRegistryOptions`.
- The registry does not persist pending input/controller state, so boot-time expiry cannot infer whether a previously hosted session was waiting for input immediately before crash.
- Exact `HostedSession` callback coverage for `touch` is delegated through event/state lifecycle and should be reviewed by Developer when selecting a future activity signal; `updatedAt` alone is not a verified semantic contract.
- Whether `needsInput` sessions are exempt, have a separate timeout, or expire after 24h remains a policy decision for Architect.

## Daemon idle lifetime, client disconnect, and configuration boundaries

### Takeaway
Client transport lifetime and hosted session lifetime are deliberately decoupled. Closing a client does not stop daemon sessions; graceful daemon stop destroys sockets and aborts/releases hosted sessions while keeping them marked for restart. There is no active-session count, daemon-idle timer, daemon lifecycle config, or automatic idle shutdown today.

### Cited Findings
- On client socket close, the server removes the socket and disposes its `ConnectionControl`; there is no call to close/release the hosted session from this handler. README says sessions keep running with no client attached, and a test verifies multiple sessions continue after every client disconnects. — [server.ts](/Users/exoulster/projects/pi-better-harness/packages/pi-better-server/src/server.ts:191), [README.md](/Users/exoulster/projects/pi-better-harness/packages/pi-better-server/README.md:1), [daemon.test.ts](/Users/exoulster/projects/pi-better-harness/packages/pi-better-server/test/daemon.test.ts:80)
- The native extension disposes its `RemoteClientSession`, closes its daemon client, and closes the SSH forward on local detach. README describes `/remote disconnect` as releasing the client connection without aborting remote work. — [extension.ts](/Users/exoulster/projects/pi-better-harness/packages/pi-better-server/src/remote-client/extension.ts:177), [README.md](/Users/exoulster/projects/pi-better-harness/packages/pi-better-server/README.md:55)
- `DaemonClient.close` destroys only its socket; on transport closure pending requests reject and close listeners run. The remote session marks itself disconnected and rejects remote operations, while `/remote disconnect` remains locally available. — [client.ts](/Users/exoulster/projects/pi-better-harness/packages/pi-better-server/src/client.ts:139), [session.ts](/Users/exoulster/projects/pi-better-harness/packages/pi-better-server/src/remote-client/session.ts:852), [remote-client-session.test.ts](/Users/exoulster/projects/pi-better-harness/packages/pi-better-server/test/remote-client-session.test.ts:712)
- `Daemon.stop` closes the listener, destroys connected sockets, calls registry shutdown, then unlinks the socket. Registry shutdown aborts/disposes live hosted sessions without changing their `running` rows, enabling later resume. — [server.ts](/Users/exoulster/projects/pi-better-harness/packages/pi-better-server/src/server.ts:213), [registry.ts](/Users/exoulster/projects/pi-better-harness/packages/pi-better-server/src/registry.ts:273)
- “Active” in the UI/browser means registry status `running` and not moved; it includes idle, running, and needs-input sessions. This differs from “currently generating” (`isStreaming`) and from “client connected” (`hasController`/socket set). — [session-browser.ts](/Users/exoulster/projects/pi-better-harness/packages/pi-better-server/src/remote-client/session-browser.ts:11), [session-browser.ts](/Users/exoulster/projects/pi-better-harness/packages/pi-better-server/src/remote-client/session-browser.ts:52), [protocol.ts](/Users/exoulster/projects/pi-better-harness/packages/pi-better-server/src/protocol.ts:21)
- `DaemonOptions` contains server dir, session options, logging, event log bounds, and companion settings only. The CLI accepts agent selection and reads `PI_SERVER_DIR`; no daemon idle timeout or session expiry setting is present. — [server.ts](/Users/exoulster/projects/pi-better-harness/packages/pi-better-server/src/server.ts:13), [cli.ts](/Users/exoulster/projects/pi-better-harness/packages/pi-better-server/src/cli.ts:7)
- Tests affirm stale-socket recovery after forced crash, survival across client disconnect, and in-process registry open/close serialization. They do not exercise auto-start, expiry, or idle shutdown. — [daemon.test.ts](/Users/exoulster/projects/pi-better-harness/packages/pi-better-server/test/daemon.test.ts:80), [daemon.test.ts](/Users/exoulster/projects/pi-better-harness/packages/pi-better-server/test/daemon.test.ts:163), [registry-lifecycle.test.ts](/Users/exoulster/projects/pi-better-harness/packages/pi-better-server/test/registry-lifecycle.test.ts:17)

### Inferences
- “Keep daemon while >=1 active session” maps most closely to persisted status `running`, not streaming or attached. Under current semantics, every created/opened session remains running until explicit close, so this rule would keep the daemon alive indefinitely absent the proposed session expiry. Architect should define whether “active” includes needs-input, moved/fenced, resume-error, and sessions with no live runtime.
- “Daemon idle 30m when 0 active sessions” requires a durable or periodic daemon-side evaluator and an authoritative zero count. Since `closed` entries remain in the registry, count must filter lifecycle status and ownership explicitly. It must also account for create/open/close races and startup resume in progress.
- If expiry closes the final running session while clients remain connected, daemon idle timing must define whether live browse/list connections reset the timer. If clients are ignored, a connected browser can lose its socket on automatic shutdown; if counted, repeated polling may keep the daemon alive. Current code tracks sockets in a set but has no activity timestamps for them.
- Auto-stop and auto-start can race: a client may connect as the final session expires or the 30-minute timer fires. A robust policy needs a single-writer lifecycle/epoch or equivalent cancellation/recheck contract covering stop, new session/open, and concurrent startup. Existing session-operation serialization is only per session and per daemon process; it does not serialize daemon start/stop across processes.
- Configuration location is open: current choices represented in code include environment (`PI_SERVER_DIR`, `PI_SERVER_AGENT`, `PI_SERVER_TMUX_SOCKET`), CLI parsing for agent selection, and programmatic `DaemonOptions`. No precedent in this package chooses whether new durations are env-only, CLI, persisted config, or extension arguments. Duration defaults (24h/30m) are user-proposed requirements, not existing defaults.
- An expired session should normally retain its JSONL and index metadata to honor current crash-recovery/transcript conventions; closing changes only hosted lifecycle and registry status in the present code. Deletion/retention would be a distinct, currently unspecified feature.

### Gaps
- There is no distinction between daemon process liveness and hosted “active session” count beyond runtime maps/index rows; no daemon heartbeat, idle timestamp, timer, service manager, or graceful auto-shutdown path is exposed.
- Current CLI lifecycle assumes an external foreground process/supervisor. The repo does not establish whether auto-start/idle-stop should launch a detached process, use systemd/launchd, or require another service boundary.
- No exact policy is established for live but unattached sessions, needs-input sessions, idle sessions, pending turns, companion terminals, transient failed resumes, sessions during move fencing, and clients that only list/refresh.
- Requested configurable 24-hour and 30-minute durations have no existing config schema/default precedence. The operational repro's machine uptime is shorter than 24 hours and is evidence about restart/socket state only, not a repository policy constraint.

## Routing

- **Developer:** trace activity callback details and implement any approved lifecycle/config behavior; add tests for expiry, restart/transcript preservation, client disconnect, and concurrent start/stop/open/create boundaries.
- **Architect:** define active-session semantics, whether needs-input/running sessions are exempt from expiry, meaning of expiry (close vs unload), daemon-idle semantics with attached clients, configuration source/precedence, and single-writer startup/shutdown protocol.
- **Researcher:** external service-manager/platform docs or evaluations of launchd/systemd and remote auto-start transport approaches. This map intentionally uses repository sources plus the operational facts supplied in the assignment, not external research.
