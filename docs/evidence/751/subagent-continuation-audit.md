## Verified behavior

- `runtime-subagent-park.test.ts` runs actual Background-enabled foreground SDK admission, a separate worker and runner, parking, foreground exit, dependency completion, resume, exact evidence reads/acknowledgement, and durable succeeded assignment outcome. Conversation ID and original capacity owner remain unchanged.
- Crash scenarios kill the server while parked, immediately after resume claim commit, after spawned launch-journal commit, after assignment result commit, after resumed bootstrap with a live writer, after published claim commit before the launch journal, and after the conversation lease is published but before the launch journal. The last window releases only the exact proven-dead manager lease under the conversation lock, with epoch fencing and no-dispatch evidence. The canonical bounded repair path is used only after proof of no dispatched/live writer. One token is retained per attempt; the external dependency operation is never relaunched.
- Live bootstrapped writers reconnect using the original private capability and stable runtime socket. Restoration checks the exact writer PID/start identity, conversation and writer lease. Capabilities are stored in owner-only files, not metadata or transcripts.
- Standalone Subagents cannot obtain Background tools simply because Server bundles them. The protected foreground grant captures compatible Background service availability and actual production tool inventory; continuation retains that captured capability.
- Admission reads canonical current permissions and intersects captured profiles. Managed scope validation accepts narrower task permissions, refuses widening, preserves protected paths, and requires mandatory authority. Tool policies intersect by exact tool name and package, ignoring list order and refusing uncaptured provenance. A real parked-worker fixture verifies narrowing unused tool permissions after foreground exit. Narrowing unused settings is allowed; removal of a frozen explicitly required tool still refuses launch under the existing loadout contract.
- Unavailable permission sources expose diagnostics and bounded exponential backoff. A 32-admissions/second root budget prevents eviction from defeating per-key backoff; diagnostics retain at most 128 generations. The real unavailable-source fixture verifies no dispatch and idle closure of runtime management after foreground detachment.
- `runtime-subagent-bootstrap-restart.test.ts` verifies stale unbootstrapped epochs cannot execute, while already bootstrapped workers resume the exact original writer and token. Transport paths are canonical and waits/cleanup are bounded.

- Changed logs for managed terminal/interrupted records flow from the existing shared inventory to manager supervision in batches of at most 128 IDs, with one outstanding batch. The manager owns one mechanical worker thread that rereads metadata/root ownership and folds canonical failure observations without opening SQLite; the query worker remains read-only. The existing derived index retains overflow and exact log versions until acknowledgement. A revocation-only shared-memory signal stops old workers on manager replacement/close; the journal remains the authority. A 128 MiB cold-log regression measured a maximum socket status latency of 4.3 ms while folding; all 132 overflow IDs retained owed failures, and a 260-ID index test verified no loss when an in-flight log revision changes. A real daemon/native SDK regression verifies a 60-second-old lost record with an already handled health callback: a malformed event appended while disconnected becomes durable owed attention, and reconnect delivers exactly that new incident once. Foreign-root records remain untouched.

- Failure-fold queue positions are fair: a changed in-flight revision moves behind existing obligations. A 260-ID regression continuously updates the first 128 orphan logs and verifies that every existing ID is served within three batches.
- Background request recovery uses a SQLite partial pending-state index and a maximum 128-row batch, yielding between batches. A migration regression seeds 10,000 completed requests with 4 KiB results plus 260 interrupted requests and unrelated non-JSON coordinator keys; the actual query plan uses the pending index, exact operation identities and completed receipts survive, and native recovery yields while draining all pending batches. Index creation is a one-time SQLite schema migration; subsequent recovery does not load returned history.
